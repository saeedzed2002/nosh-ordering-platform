# Phase 16 — Mobile-ready contract and final documentation

Phase 16 freezes the current local-demo contract for a future native client.
It documents existing behavior; it does not add a mobile application, a
production integration, or a second implementation of ordering rules.

## Contract source of truth

| Artifact | Purpose | Ownership |
| --- | --- | --- |
| `docs/contracts/openapi-v1.json` | Sorted OpenAPI `3.1.0` snapshot for every public `/api/v1` route. | Generated by `backend/scripts/export_openapi.py`. |
| `frontend/src/api/generated/v1.ts` | Generated TypeScript declarations from that snapshot. | Generated by `npm run generate:api`. |
| `frontend/src/api/v1.ts` | Stable aliases consumed by customer catalog code. | Hand-maintained adapter only; never duplicates generated shapes. |
| `backend/tests/test_phase_16_contract.py` | Fails when FastAPI's generated public contract and the committed snapshot differ. | Backend test suite. |

The OpenAPI document currently identifies the application as `Nosh API`
version `0.1.0`; the compatibility boundary is the URL namespace `/api/v1`.
The API root returns `{ "name": "Nosh API", "version": "v1" }`.

### Compatibility policy

- Do not rename, remove, or change the meaning of an existing `/api/v1` field,
  enum value, validation rule, or status code without a consumer migration.
- Prefer additive optional response fields and additive endpoints within `v1`.
- Add a new route namespace such as `/api/v2` for an incompatible public
  consumer change. Never silently reinterpret an order status or stored amount.
- Regenerate and review both artifacts in `docs/contracts/` and
  `frontend/src/api/generated/` after an intentional contract change. CI
  rejects drift.

## Client integration rules

The native client base URL is environment-provided. For this demo it is
`http://localhost:8000`; all application routes live under `/api/v1`.

| Area | Contracted routes | Client rule |
| --- | --- | --- |
| Catalog | `/catalog/home`, `/catalog/menu-items`, `/catalog/locations`, `/catalog/cart/quote` | Treat catalog data as current server state; cache only with an explicit refresh policy. |
| Authentication | `/auth/customer/sign-up`, `/auth/customer/sign-in`, `/auth/admin/sign-in`, `/auth/refresh`, `/auth/me` | Send a bearer access token only to authenticated routes. Refresh tokens must never be placed in a URL or application log. |
| Checkout and tracking | `/orders/checkout`, `/orders/{publicReference}` | Generate and retain one idempotency key per checkout intent. A public order reference is not an authorization credential. |
| Customer account | `/account/*` | The server owns account filtering. A foreign object produces the same generic `404` as a missing object. |
| Administration | `/admin/*` | Present only role-permitted actions, but rely on the server for authorization and state transitions. |

Generated schema aliases are already used by `customerCatalog.ts` for menu,
location, cart-quote, and public-review responses. New client work should
import the generated `paths` or the stable aliases in `api/v1.ts`; it should
not reproduce server response shapes by hand.

## Error and state contract

| Situation | HTTP behavior | Native-client behavior |
| --- | --- | --- |
| Request validation | `422` with FastAPI `HTTPValidationError.detail` entries. | Highlight the relevant input when possible; otherwise show a safe general correction message. |
| Missing or foreign owned resource | `404` with a generic detail. | Do not distinguish ownership from absence. |
| Missing, expired, inactive, or malformed authentication | `401`. | Clear only the affected session and return to sign-in with a safe destination. |
| Authenticated but forbidden role | `403`. | Explain that the role lacks access; do not expose hidden data. |
| Current server rule conflict | `409`, for example stale cart eligibility, idempotency mismatch, capacity, or paused ordering. | Refresh catalog/quote or show the server-provided safe conflict detail; never force a stale client total. |
| Unexpected response or network failure | No trusted domain result. | Preserve editable local input where safe, show retry, and avoid inventing an order, payment, or courier state. |

Domain errors are returned as a safe JSON `detail` string. The existing web
client centralizes that parsing in `ApiError`; a native client should keep the
same separation between structured validation errors and safe domain messages.

## Ordering invariants that mobile must not reimplement

1. A cart is only a local draft. `POST /catalog/cart/quote` validates current
   publication, availability, option ownership and limits, currency, quantity
   from `1` through `20`, and location eligibility before a quote is trusted.
2. Checkout is the only command that creates an order. It requires an
   idempotency key, repeats quote validation, applies a current promotion
   atomically, and writes immutable item, price, option, care, fulfilment, and
   status snapshots.
3. A mock payment decline creates no order. No mobile UI may claim card capture
   or money movement for this local demo.
4. `submitted` and `scheduled` are initial order outcomes. Staff can only move
   an order to a server-provided next status; sensitive `declined` and
   `cancelled` actions require manager or owner authorization and a controlled
   customer-safe reason.
5. Public receipts and trackers remain redacted. Recipient contact details,
   delivery address, kitchen instructions, refresh tokens, and audit metadata
   are not public-mobile data.
6. Reorder returns a newly validated draft and never copies a historical total.
   Reviews require an account-owned delivered order item and remain pending
   until staff moderation.

## Design and component contract

The native interface should preserve semantic roles and state behavior, not
web-specific layout code. `docs/phase-2-design-system.md` remains the visual
token source; the current key tokens are warm canvas `#F6F1E8`, raised surface
`#FFFDF8`, inverse olive `#0D2417`, action orange `#FF6A16`, and textual
available/preparing/ready/unavailable statuses.

| Primitive | Required states | Non-negotiable behavior |
| --- | --- | --- |
| Primary and destructive action | default, pressed, disabled, loading, error | Native accessible action semantics; loading does not permit a duplicate submission. |
| Field and select | default, focus, hint, invalid, disabled | Visible label, error association, and no color-only validation. |
| Quantity control | min, max, disabled, live value | Named increment/decrement controls and a numeric value always visible between them. |
| Dialog or confirmation | closed, open, keyboard dismissal, validation error | Initial focus, focus trap, Escape dismissal, and focus restoration. |
| Order status | submitted, active, ready, completed, issue | Text and timestamp accompany status color; no fabricated live courier state. |
| Motion | default and reduced motion | Motion is decorative only and must not communicate an order, payment, or delivery fact. |

## Future native requirements, explicitly not implemented now

| Future capability | Current local-demo state | Production/mobile prerequisite |
| --- | --- | --- |
| Push notifications | Not implemented. | Consent, device-token registration, delivery provider, retry/observability, and account-bound notification preferences. |
| Live courier location | Not implemented; tracker polls recorded kitchen status only. | Courier identity, consent, secure location ingestion, throttling, retention/deletion rules, and map-provider agreements. |
| In-app payments | Simulated approve/decline only; no card data accepted or stored. | PCI-scoped provider integration, server-side payment intent lifecycle, webhook verification, refunds, reconciliation, and fraud controls. |
| Secure native storage | Browser sessions are local to the current browser storage model. | Platform keystore/keychain storage, token rotation, biometric policy, logout/revocation, backup policy, and threat-model review. |
| Production operations | No deployment or external providers. | HTTPS, managed secrets, backup/restore drills, monitoring, rate limits, incident process, data-retention policy, and legal/compliance review. |
